### 1.1 Test-time prompt grouping is a dead end at this accuracy

Prompt recovery is essentially solved (ARI 0.988, purity 0.994). The tricks built on top of it
are not, because they repair *collisions* and a 0.66 model collides far less than the weak
members everyone measured them on:

| base BA | assignment gain | collision rate |
| --: | --: | --: |
| 0.25 | +0.092 | 0.72 |
| 0.45 | +0.032 | 0.65 |
| 0.55 | +0.020 | 0.54 |
| **0.66** | **0.000** | 0.49 |
| 0.70 | −0.012 | 0.41 |

This one curve explains every public report that looked contradictory: 751802's Hungarian
OOF +0.107 with a flat LB, 752357's "flat to negative", 752708's LB tracking the thin-cluster
columns. They were all measuring a lever that had already saturated on their own blend.

### 1.2 v20 is already correctly tuned — verified, not assumed

`--adapt_w` weights a centred twin computed as `head(Z − mean_cluster(Z))`. Because the head is
affine, that is *exactly* log-prob-space mean centring at w=1, so the shipped setting has an
effective centring weight of `adapt_w·twin/(1+adapt_w·twin)` = `0.35/1.35` = **0.259**, and the
sweep in §1.1 puts the optimum at 0.25. A v21 drafted to "fix" this was retracted before
submission (`notebooks/v21/` deleted, `experiments/39_build_v21.py` kept as the record) because
it would have moved the effective weight to 0.08, i.e. away from the optimum.

**There is no inference-only lever left.** Weights, centring, cut, Sinkhorn 0.45 and ATLAS 0.20
are each measured-optimal or worth ≤0.003. The 0.660 base is not leaving points on the table.

## 2. What the remaining 0.067 to #1 is made of

Blend arithmetic from `docs/research/frontier-2026-10-29.md` §6: frozen LoRA/encoder members
carry 10.5 of ~12.4 weight (~85%). The refittable share is ~12%, so a member-level gain of
+0.034 is worth ≈ +0.004 on the blend. Every published incremental improvement is consistent
with this: 27B GSQ head +0.001, ATLAS 0.10→0.20 +0.003, our own pool+centred member +0.007.

To reach 0.728 the blend needs +0.067. At the 12% share that requires member-level gains of
roughly +0.55 absolute, which no member-level change can deliver. **The weight share has to
change, which means the new members have to be strong enough to earn real weight — that is a
training job, not a blending job.**

## 3. The campaign (needs GPU; quota refreshes 2026-10-31 00:00 UTC)

The only lever with documented headroom is member training on the 245k open pool, which we
currently use *only* for the TF-IDF SVC members and *not* for any LLM member. 752810 measured
pool 36k→124k as SVC 0.436→0.467 and **blend LB 0.586→0.617 (+0.031)** — the largest single
documented jump in this competition.

Pool inventory (`/tmp/pool/ntl_open_pool.parquet`): 245,081 clean rows, 89,730 prompt groups,
6,030-21,027 rows per model, mean 120 words, all 18 labels present. Leakage flags already
computed and applied (`flag_near_train_prompt`, `flag_train_prompt_regen`,
`flag_gemini37_routing_risk`).

### 3.1 Step 0 — per-member OOF harness (no GPU, do first)

We hold **no** OOF log-probabilities for any frozen member, which is why every blend change so
far has been a guess. Before adding members, dump per-member OOF log-probs on train using the
existing `ts_q3b8_f{k}` per-fold adapters, so weights and ATLAS/mix choices become fitting
problems instead of submissions. Without this, step 2 cannot be evaluated.

### 3.2 Step 1 — train diverse members on the pool

753177: member OOF 0.569→0.605 but LB 0.651→0.647 — **diversity beats strength**. So pick
backbones *not* already in the blend (Qwen3-14B/8B/4B, Qwen2.5-7B/14B, Llama-3.1-8B, GLM-4-9B,
DeBERTa-v3-large, UltraBERT, ELECTRA are all taken):

1. `allenai/OLMo-2-1124-7B` — Dolma corpus, the most different pretraining distribution available.
2. `mistralai/Mistral-7B-v0.3` — different tokenizer and corpus again.
3. A second seed / truncation-augmented OLMo if 1 and 2 land.

Recipe: truncated base (`keep` 14-24 layers, as the existing l24 members do — this is what makes
2×T4 viable), LoRA r=16 α=32 on all linear projections, `max_len` 320-384, masked mean-pooled
multi-layer features → linear head, fp16 (`no bfloat16` on Turing; the pipeline already has the
bf16-retry guard for overflow). Random 40-80 word truncation on ~20% of rows (AGENTS.md §4.3:
under-60-word passages score 0.27 vs 0.46 over 160). Fit on 60-100k pool rows, 1-2 epochs, then
calibrate on official `train.csv`. Budget ≤6 h per kernel run to stay inside the 9 h cap.

### 3.3 Step 2 — admit a member only on measured blend gain

Using step 0's harness: add one member at a time, refit blend weights on OOF, and require
+0.005 blend OOF before spending a submission. Expect the first new backbone to be worth
+0.005-0.015; two or three diverse ones to compound because the ensemble error decorrelates.

### 3.4 Submission discipline

- Confirm before spending the last daily submission or either Final Submission.
- Public 3-row test is all singletons, so every grouping path is invisible to the commit gate —
  only a rerun exercises them. Do not use the commit gate as evidence for grouped behaviour.
- Same-notebook rerun noise is ±0.004-0.006 (753177); do not chase differences inside that band.
